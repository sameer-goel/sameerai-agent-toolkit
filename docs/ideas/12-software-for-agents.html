#12 Software for Agents

STRONGEST FIT

The Problem (from YC)

"The next trillion users on the internet will be AI agents. They need completely different software."

"While everyone else is building agents, the biggest opportunity might be building the software those agents depend on."
- Aaron Epstein, YC Partner

Agents perform browsing, research, purchasing, CRM management on interfaces designed for humans. This creates slowness, inconsistency, fragility. YC wants: machine-readable interfaces, APIs, MCPs, CLIs with thorough documentation and discovery tools.

The Gap (What's Missing)

Nobody is solving:

  • Agent self-organization: agents that learn what tools to use without being told each time. Existing solutions require explicit wiring.
  • Cross-model skill portability: skills written for Claude don't work in GPT or Gemini. No universal skill format.
  • Cost-aware routing: agents burn expensive models on simple tasks. No one auto-routes cheap model for reads, expensive for architecture.
  • Memory persistence that works: agents forget everything between sessions. LangChain memory is crude (full chat history). No structured, typed, pruning memory.
  • Agent-to-agent handoff: Claude can't delegate to Codex mid-task. No bridge protocol for multi-vendor agent collaboration.

Cross-model portability Not solved yet. Skills are Claude Code specific (markdown SKILL.md format). GAP

My unique angle vs existing players:

  • Composio/Arcade give agents tools. I give agents the ability to discover which tool to use and route to the cheapest model that can handle it.
  • LangChain is a framework you build on. Mine is a layer that wraps any existing agent (Claude Code, Codex, Kiro) without replacing it.
  • MCP is the protocol. I build the intelligence layer ON TOP: which MCP to call, when, with what model, and remember why.

What to Build Next

To make this a product (not just personal tooling):

  1. Make skill-matcher framework-agnostic. Currently reads Claude Code SKILL.md. Should read: OpenAPI specs, MCP manifests, function schemas, tool descriptions from any source.
  2. Package model-router as standalone. pip install, npm install, or single binary. Config file for tiers + model IDs. Works with any LLM provider.
  3. Memory protocol as a service. API: store, recall, prune. Not tied to filesystem. Could be SaaS (hosted memory for agents) or OSS (self-hosted).
  4. Demo: "agent that gets smarter each session." Record 5 sessions. Show the agent remembering corrections, routing efficiently, discovering new skills. That's the YC demo.

Minimum effort to validate:

  • Extract model-router into standalone pip package (2h)
  • Add OpenAPI spec scanning to skill-matcher (4h)
  • Record demo video showing memory + routing in action (1h)
  • Post on HN Show HN + r/ClaudeAI + X (30min)

Competitive Positioning

DimensionExisting solutionsMy approach
Model Single-model (LangChain = OpenAI-first, CrewAI = one model per agent) Multi-model by default. Route per task.
Memory Chat history buffer or vector store (crude, no types, no pruning) Typed, layered, auto-pruning. Structured capture.
Discovery Explicit wiring (you tell the agent what tools exist) Auto-discovery from skill descriptions. Agent finds what it can do.
Cost Fixed model, no routing. Burns expensive tokens on simple tasks. Regex classifier in <50ms. 3x cost reduction on simple ops.
Vendor lock-in Framework-specific (LangChain, CrewAI) or platform-specific (OpenAI Actions) Wrapper pattern. Sits on top of any agent. No rewrite needed.
